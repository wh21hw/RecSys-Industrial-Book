推荐大模型

大语言模型（LLM）的崛起深刻改变了人工智能的技术格局。从 GPT-3 到 GPT-4、从 LLaMA 到 Qwen，大模型在自然语言理解、生成、推理方面展现出前所未有的能力。推荐系统作为 AI 最重要的落地场景之一，自然也受到大模型浪潮的深刻影响。本章将系统介绍大模型在推荐系统中的应用——从 LLM 作为特征增强到 LLM 作为推荐引擎，再到推荐领域的基础模型和 Scaling Law。

35.1 LLM 与推荐系统的交汇

35.1.1 范式演进

大模型在推荐系统中的应用经历了三个阶段的演进：

阶段一：LLM 作为特征增强器（2022-2023）。使用 LLM 的 embedding 或生成能力为传统推荐模型提供增强特征。例如，使用 LLM 生成物品描述、提取用户兴趣标签、编码文本语义。这种方式不改推荐架构，只是用 LLM 替代传统 NLP 模块。优势是兼容性好、风险低，劣势是未充分利用 LLM 的推理能力。

阶段二：LLM 作为推荐引擎（2023-2024）。直接使用 LLM 进行推荐推理。将用户历史和候选物品编码为 prompt，输入 LLM 生成推荐结果。这种方式利用了 LLM 的推理和泛化能力，但面临推理延迟高、候选集受限等挑战。代表工作：P5、NIRRTU、LLMRank。

阶段三：推荐领域基础模型（2024-2025）。构建推荐领域的"基础模型"——在大规模推荐数据上预训练，具备通用推荐能力，可适配多种下游推荐任务。这种思路借鉴了 LLM 的预训练-微调范式。代表工作：Meta 的 HSTU 可以看作推荐基础模型的雏形。

35.1.2 技术路线

LLM 与推荐系统结合的技术路线可以分为以下几类：

路线一：LLM Embedding 注入。使用 LLM 的 embedding 层输出作为物品或用户的特征表示，注入传统推荐模型。这种方式利用了 LLM 预训练获得的丰富语义知识，且不改变推荐架构。

路线二：LLM 生成式推荐。将推荐问题转化为 LLM 的生成任务。通过 prompt engineering 或指令微调，让 LLM 直接输出推荐结果。

路线三：LLM + Agent 推荐。将 LLM 作为推荐 Agent 的大脑，通过工具调用（Tool Calling）和检索增强生成（RAG）实现复杂推荐流程。Agent 可以调用召回模型、排序模型、知识库等工具，实现超越单一模型的推荐能力。

路线四：推荐领域大模型预训练。在推荐数据上从头预训练大模型，学习推荐领域的通用知识和模式，然后适配到具体场景。

35.1.3 核心挑战

推理延迟：LLM 的推理延迟（通常 100ms-1s）远超传统推荐模型（< 10ms），难以满足实时推荐的要求。解决方案包括：模型蒸馏、量化、speculative decoding、将 LLM 用于离线而非在线。

候选集限制：LLM 的上下文窗口有限（通常 4K-32K token），无法在 prompt 中列出全部候选物品（百万级）。解决方案包括：RAG 检索增强、分层推荐（先召回再 LLM 排序）、物品 ID 压缩。

幻觉问题：LLM 可能推荐不存在的物品或生成不准确的信息。解决方案包括：constrained decoding、后处理验证、grounding 检索增强。

成本：LLM 的训练和推理成本远高于传统推荐模型。需要权衡效果提升与成本增加。

评估挑战：LLM 推荐的效果评估比传统模型复杂——除了准确率指标，还需要评估推理质量、可解释性、安全性等。

35.2 LLM 作为特征增强

35.2.1 LLM Embedding 注入

使用 LLM 的 embedding 作为推荐模型的特征是最简单直接的 LLM 增强方式。具体做法：

（1）物品 embedding：将物品标题、描述、评论等文本拼接后输入 LLM，取倒数第二层的平均 pooling 作为物品的文本表示。该向量可以作为推荐模型的辅助特征。

（2）用户 embedding：将用户的历史行为序列描述为自然语言（如"用户最近浏览了：连衣裙、凉鞋、太阳帽"），输入 LLM 获取用户兴趣表示。

（3）融合方式：LLM embedding 可以与 ID embedding 拼接、加权融合或通过交叉注意力交互。实践中，拼接 + MLP 是最常用的方式。

效果：多个工业实践表明，LLM embedding 注入可以使推荐模型 CTR 提升 1-3%，尤其对冷启动物品和长尾物品效果显著（提升 5-10%）。因为 LLM embedding 携带了丰富的语义知识，弥补了 ID embedding 对新物品的不足。

35.2.2 LLM 知识增强

LLM 蕴含了丰富的世界知识，可以用于推荐系统的知识增强：

物品知识生成：使用 LLM 为物品生成结构化知识——属性标签、类别、风格、适用场景等。例如，给定一个商品标题"红色碎花连衣裙"，LLM 可以生成：类别=连衣裙、颜色=红色、图案=碎花、风格=甜美、季节=夏季、场景=约会/度假。这些结构化标签作为推荐模型的离散特征。

用户兴趣画像：使用 LLM 分析用户行为序列，生成自然语言兴趣画像。例如，"该用户对户外运动和摄影感兴趣，偏好高性价比产品，近期关注露营装备"。这种画像可以用于召回策略选择和推荐理由生成。

知识图谱增强：使用 LLM 补充推荐知识图谱中的缺失关系。例如，LLM 可以推断"登山鞋"与"户外运动"的从属关系、"防晒霜"与"夏季"的季节关联等。

35.2.3 LLM 推理特征

LLM 的推理能力可以生成传统方法难以提取的高阶特征：

搭配推荐特征：LLM 可以推理物品间的搭配关系——"这条牛仔裤搭配什么上衣合适？"LLM 生成搭配建议，作为推荐模型的交叉特征。

场景推理特征：LLM 推理用户当前场景——"用户最近浏览了帐篷、睡袋、登山杖，推断正在准备露营活动"。这种场景推理特征可以用于推荐场景化物品组。

意图理解特征：LLM 理解用户搜索意图——"夏季显瘦"不仅匹配单品，还理解"显瘦"的视觉效果需求。这种深层意图理解可以提升搜索推荐的相关性。

35.3 LLM 作为推荐引擎

35.3.1 Prompt-based 推荐

直接使用 LLM 的 in-context learning 能力进行推荐。将用户历史和候选物品编码为自然语言 prompt，输入 LLM 输出推荐结果。

基础 prompt 模板：

"用户历史行为：{item1}, {item2}, ..., {itemN}
候选物品：{cand1}, {cand2}, ..., {candM}
请从候选物品中选择用户最可能感兴趣的 Top-K。"   (35.1)

效果：研究表明，GPT-4 在零样本推荐场景中可以取得接近传统推荐模型的效果，尤其在用户历史丰富、候选集较小的情况下。但在大规模工业场景中，由于候选集限制和推理延迟，纯 prompt 推荐尚不实用。

优化策略：

（1）few-shot prompting：在 prompt 中加入几个推荐示例，引导 LLM 理解推荐任务格式。

（2）chain-of-thought 推荐：让 LLM 先推理用户兴趣，再给出推荐结果。"先分析用户可能感兴趣的方向，然后从候选中选择最匹配的物品。"

（3）结构化 prompt：使用 JSON 或 YAML 格式组织 prompt，提高 LLM 理解效率。

35.3.2 指令微调推荐

通过在推荐数据上对 LLM 进行指令微调（instruction tuning），使其获得专门的推荐能力。代表工作 P5（Pretrain, Personalized Prompt, Predict Paradigm）：

P5 框架：将多种推荐任务统一为文本到文本的生成任务：

（1）评分预测："给定用户和物品，预测评分（1-5）。"

（2）序列推荐："给定用户历史 {item1, ..., itemN}，预测下一个物品。"

（3）推荐解释："解释为什么向该用户推荐该物品。"

（4）对话推荐：多轮对话理解用户需求并推荐。

（5）评论摘要：生成物品评论摘要辅助推荐。

通过在多个推荐任务上联合微调，P5 获得了通用的推荐能力，在多个任务上达到或超过传统专用模型。

35.3.3 NIRRTU 与 LLMRank

NIRRTU（Navigating Item Retrieval with LLMs）：使用 LLM 进行物品检索。将推荐召回重新定义为 LLM 的生成任务——给定用户历史，LLM 生成可能感兴趣的物品描述，然后通过描述检索物品。

LLMRank：使用 LLM 对候选物品进行排序。将候选物品列表输入 LLM，让 LLM 输出排序后的列表。研究表明，LLM 排序在候选集较小时（< 20）效果接近传统精排模型，但在大规模场景中不实用。

35.4 推荐领域基础模型

35.4.1 推荐大模型预训练

借鉴 LLM 的预训练范式，在推荐数据上预训练大模型是当前的前沿方向。核心思路是：在海量推荐数据（用户行为日志、物品内容、评论等）上预训练一个大规模 Transformer 模型，使其获得通用的推荐能力，然后适配到具体场景。

预训练数据：

（1）用户行为序列：从历史日志中提取用户-物品交互序列，作为主要的预训练数据。

（2）物品内容：物品标题、描述、图片、视频等多模态信息。

（3）用户评论：评论文本提供了丰富的偏好信号。

（4）知识图谱：物品间的语义关系和属性信息。

预训练任务：

（1）掩码物品预测（Masked Item Prediction）：随机遮盖用户序列中的部分物品，让模型预测被遮盖的物品。类似 BERT 的 MLM 任务。

（2）下一物品预测（Next Item Prediction）：给定前 n-1 个物品，预测第 n 个物品。类似 GPT 的自回归预测。

（3）对比学习：拉近同一用户的不同行为序列，推远不同用户的序列。

（4）多任务预训练：同时优化评分预测、序列推荐、评论生成等多个任务。

35.4.2 领域适配

预训练的推荐大模型需要适配到具体场景：

指令微调：在目标场景的小规模数据上进行指令微调，使模型适配特定场景的推荐格式和偏好。

RLHF/DPO 对齐：使用用户反馈（点击、购买、评分）作为偏好信号，通过 RLHF 或 DPO 对齐模型，使其更符合用户真实偏好。

场景适配层：在预训练模型上添加场景特定的适配层（adapter），用少量场景数据微调适配层而非全量参数。

35.4.3 推荐基础模型的挑战

数据规模与质量：推荐预训练需要海量高质量行为数据。与 LLM 可以利用互联网文本不同，推荐数据通常是平台私有的，数据获取和跨平台共享受限。

评估标准缺失：推荐基础模型缺乏统一的评估基准。不同平台的数据分布、物品集、用户群体差异大，难以建立通用 benchmark。

计算成本：推荐大模型的预训练需要大量 GPU 资源。如何平衡模型规模、数据量和效果是关键问题。

领域知识 vs 通用知识：推荐场景的领域知识（如用户偏好、物品关系）与 LLM 的通用世界知识不同。如何在 LLM 通用知识基础上注入推荐领域知识是核心挑战。

35.5 推荐系统的 Scaling Law

Scaling Law 是大模型时代的核心发现之一——模型效果随参数量、数据量和计算量按幂律提升。推荐系统是否也存在类似的 Scaling Law？这是当前推荐领域的热点研究方向。

35.5.1 数据缩放

行为数据缩放：研究表明，推荐模型的效果随训练数据量按幂律提升，但存在饱和点。与传统 LLM 不同的是，推荐数据的"质量"比"数量"更重要——高质量的用户行为（点击 + 购买）比低质量行为（曝光 + 点击）对模型提升更大。

序列长度缩放：HSTU 的研究表明，用户行为序列长度从 200 扩展到 8192 时，效果持续提升。这表明推荐模型从更长历史中受益，但计算开销也线性增长。

物品数量缩放：物品库规模对模型效果的影响是非线性的——当物品数从万级扩展到百万级时效果显著提升，但从百万到亿级的提升幅度减小（因为长尾物品数据不足）。

35.5.2 模型缩放

参数量缩放：推荐模型的参数量从百万级（早期 DNN）扩展到十亿级（HSTU），效果按幂律提升。但推荐模型的 Scaling Law 与 LLM 有差异——推荐模型的效果饱和点可能比 LLM 更早出现，因为推荐任务比语言建模更简单。

特征维度缩放：特征维度（embedding size、隐藏层维度）的缩放效果在推荐场景中呈现递减效应——从 32 维到 128 维提升显著，但从 512 到 1024 的提升较小。

训练步数缩放：推荐模型通常训练 1-2 个 epoch（one-epoch principle），与 LLM 的多 epoch 训练不同。研究表明，推荐模型在 1 epoch 后继续训练可能过拟合，这与推荐数据的特性有关。

35.5.3 特征缩放与推荐 Scaling Law 的特殊性

特征数量缩放：推荐模型的特征数量（从几十到几千）对效果的影响比模型参数更大。增加新特征（如多模态特征、上下文特征）的效果往往超过增加模型参数。

推荐 Scaling Law 的特殊性：

（1）One-epoch 现象：推荐模型通常只训练一个 epoch，这与 LLM 的多 epoch 训练不同。原因是推荐数据中每个样本只出现一次，多次 epoch 会导致过拟合。

（2）特征重要性：推荐模型的效果更多取决于特征工程而非模型规模。这与 LLM 主要靠参数规模不同。

（3）数据分布漂移：推荐数据的分布随时间快速变化（新物品、新用户、趋势变化），模型需要持续更新而非一次训练。

（4）多目标复杂性：推荐系统通常优化多个目标（CTR、CVR、多样性等），Scaling Law 在多目标场景中更复杂。

35.6 Scaling Up 推荐模型：工业前沿

2024-2025 年，推荐系统领域出现了一系列重要的 Scaling Up 工作——将推荐模型参数量从亿级推向百亿甚至千亿，同时通过硬件感知设计将模型 MFU（Model FLOPS Utilization）从不到 5% 提升到 45%+。这些工作代表了推荐系统从"小模型+多模块"向"大模型+统一架构"的范式转变。本节系统介绍 RankMixer、OneTrans、HyFormer、Kunlun、Wukong 等前沿工作。

35.6.1 Wukong：堆叠 FM 的 Scaling Law

Wukong 由快手于 2024 年提出，是首个在推荐系统领域建立完整 Scaling Law 的工作。Wukong 的核心发现是：推荐模型可以通过堆叠因子分解机（Stacked Factorization Machine）实现有效缩放，而不需要依赖复杂的 Transformer 架构。

架构设计：Wukong 完全基于堆叠 FM 层构建——每层是一个因子分解机，通过学习特征间的高阶交互来提升模型表达力。与传统 DeepFM/DCN 不同，Wukong 将 FM 层堆叠到 20-100 层，通过深度堆叠实现 Scaling Up。关键创新在于设计了残差连接和层归一化机制，使得深层 FM 也能稳定训练。

Scaling Law 发现：Wukong 系统性地验证了推荐模型的 Scaling Law——模型效果随参数量、数据量和训练步数按幂律提升。但推荐 Scaling Law 与 LLM 有两个关键差异：（1）One-epoch 现象——推荐模型通常只训练一个 epoch，多 epoch 训练反而过拟合；（2）特征重要性——增加特征数量比增加模型参数更有效。

协同缩放策略：Wukong 提出了"协同缩放"（Synergistic Upscaling）策略——同时缩放模型深度、特征维度和数据量，三者按最优比例增长。单独缩放任何一个维度都会导致效果饱和，只有协同缩放才能实现持续提升。

35.6.2 Kunlun：MFU 优化与 Scaling Law

Kunlun 由快手于 2025 年提出，是首个为推荐系统建立完整 Scaling Laws 并系统优化 MFU 的工作。Kunlun 的核心贡献是通过硬件感知的架构设计，将推荐模型的 MFU 从 17% 提升到 37%（在 NVIDIA B200 GPU 上），实现了 2 倍的缩放效率提升。

MFU 瓶颈分析：Kunlun 首先系统分析了推荐模型的 MFU 瓶颈——传统推荐模型的 Embedding 查表操作导致 GPU 利用率极低（<5%），因为 Embedding 查表是内存密集型而非计算密集型。Kunlun 通过将 Embedding 查表优化为密集矩阵运算，大幅提升了 GPU 计算利用率。

架构创新：Kunlun 的架构设计围绕硬件感知展开——（1）将稀疏 Embedding 查表转化为密集 Batch 操作；（2）使用 FlashAttention 加速 Transformer 注意力计算；（3）设计混合精度训练策略，Embedding 用 FP32、其他层用 BF16；（4）引入序列并行和数据并行的混合并行策略。

Scaling Laws：Kunlun 建立了推荐系统的完整 Scaling Laws，包含三个维度：

  • 模型缩放：参数量从 1B→10B→100B，效果按幂律提升
  • 数据缩放：训练样本从 10B→100B→1T，效果持续提升但递减
  • 序列缩放：用户行为序列从 512→4096→32768，效果显著提升

三个维度的最优缩放比例为 模型:数据:序列 ≈ 1:10:2，偏离此比例会导致效果饱和。

35.6.3 RankMixer：硬件感知统一架构

RankMixer 由 2025 年提出（被引 90+ 次），是 Scaling Up 排序模型的标志性工作。RankMixer 的核心创新是硬件感知的统一特征交互架构，将模型 MFU 从 4.5% 提升到 45%——10 倍效率提升，使得排序模型参数量可以扩展到百亿级。

问题动机：传统排序模型（如 DIN、DIEN、BST）使用多种手工设计的低 MFU 模块——注意力模块、序列建模模块、特征交叉模块等。这些模块各自优化了算法效果，但整体 MFU 极低（<5%），导致 GPU 资源严重浪费。当尝试扩大模型参数时，低 MFU 使得训练成本不可承受。

统一架构：RankMixer 用统一的 Mixer 架构替代了多种手工模块。Mixer 层通过转置矩阵乘法同时实现特征间交互和特征内变换，计算模式高度规则化，GPU 友好。所有特征交互、序列建模和特征变换都通过堆叠 Mixer 层实现，消除了低 MFU 的手工模块。

硬件感知设计：RankMixer 的设计以 GPU 计算特性为约束——（1）所有计算都是密集矩阵乘法，无稀疏操作；（2）张量形状对齐 GPU warp 大小（32/64）；（3）层间计算量均衡，避免流水线气泡；（4）支持 Tensor Core 加速。这些设计使 RankMixer 的 MFU 达到 45%，接近理论极限。

缩放效果：RankMixer 在工业实践中将排序模型参数从亿级扩展到百亿级，在保持延迟不变的前提下，线上 CTR 提升 3-5%。MFU 从 4.5%→45% 意味着相同 GPU 资源可以训练 10 倍大的模型。

35.6.4 OneTrans：统一 Transformer 骨干

OneTrans 由 2025 年提出（被引 54+ 次），是首个将特征交互和序列建模统一到单一 Transformer 骨干的推荐模型。OneTrans 的核心思想是：用统一的 Transformer 同时处理特征交互和用户行为序列建模，而非传统方案中用不同模块分别处理。

传统方案的局限：传统排序模型中，特征交互（DCN/FM）和序列建模（DIN/BST）使用不同的架构——特征交互是浅层全连接，序列建模是深层 Transformer。这种分离导致：（1）特征交互和序列建模无法深度交互；（2）两种架构的计算模式不同，MFU 低；（3）系统复杂度高，维护困难。

统一 Transformer：OneTrans 将所有特征（用户特征、物品特征、上下文特征、行为序列）统一编码为 Token 序列，输入统一 Transformer 骨干进行联合建模。特征交互通过 Transformer 的自注意力自然实现——不同特征的 Token 通过注意力交互。序列建模也通过同一 Transformer 实现——行为序列 Token 通过自注意力建模时序依赖。

Scaling 到十亿参数：OneTrans 验证了统一 Transformer 骨干可以 Scaling 到十亿参数级别。关键发现是：统一架构的 Scaling Law 比分离架构更优——参数量从 100M→1B→10B，效果持续提升且无饱和迹象。这表明统一架构比分离架构有更好的缩放性质。

LLM 系统优化复用：OneTrans 的统一 Transformer 架构可以直接复用 LLM 领域的系统优化——FlashAttention、KV Cache、Tensor Parallelism、Pipeline Parallelism 等。这些优化在 LLM 领域已经成熟，OneTrans 将其引入推荐系统，大幅降低了工程成本。

35.6.5 HyFormer：混合 Transformer 架构

HyFormer 于 2025 年提出，是 OneTrans 的进一步发展。HyFormer 的核心创新是统一混合 Transformer 架构——在单一模型中实现长序列建模和特征交互的双向、层级间交互。

OneTrans 的局限：OneTrans 虽然统一了特征交互和序列建模，但两者在 Transformer 层内是"并列"的——特征 Token 和序列 Token 在同一层通过自注意力交互，但不同层之间缺乏专门的交互机制。这导致深层网络中特征交互和序列建模可能"解耦"。

HyFormer 的混合架构：HyFormer 设计了双向层级间交互机制——在每一 Transformer 层中，特征交互分支和序列建模分支通过交叉注意力（Cross-Attention）进行双向交互。特征交互分支为序列建模提供上下文信息（用户画像、物品属性），序列建模分支为特征交互提供行为信号（用户兴趣、时序模式）。

层级间交互：HyFormer 的层级间交互不仅限于同一层，还通过跨层连接实现跨层交互——浅层的特征交互结果直接传递到深层的序列建模分支，深层的序列建模结果反馈到浅层的特征交互分支。这种跨层交互使得模型可以在不同抽象层次上融合信息。

长序列支持：HyFormer 通过线性注意力和层次化建模支持超长行为序列（万级+）。线性注意力将复杂度从 O(n²) 降低到 O(n)，层次化建模通过分层聚合进一步降低计算量。这使得 HyFormer 可以在统一架构中同时处理特征交互和万级长序列建模。

35.6.7 技术趋势分析

Scaling Up 推荐模型的演进呈现以下核心趋势：

（1）从分离架构到统一架构。传统推荐模型用不同模块分别处理特征交互、序列建模、多任务——DCN 做特征交叉、DIN 做序列建模、MMoE 做多任务。OneTrans/HyFormer 将这些功能统一到单一 Transformer 骨干，消除了模块间的割裂，同时大幅提升 MFU。

（2）从算法优化到硬件感知。RankMixer/Kunlun 的核心创新不是新算法，而是硬件感知设计——将计算模式对齐 GPU 特性，消除稀疏操作，使用密集矩阵乘法。这代表了推荐系统从"算法驱动"到"系统驱动"的范式转变。

（3）从手工模块到堆叠骨干。传统推荐模型依赖大量手工设计的模块（DIN 注意力、DIEN GRU、BST Transformer）。Wukong/RankMixer 证明，通过堆叠简单但高效的骨干层（FM/Mixer），可以达到甚至超越手工模块的效果，同时大幅提升 MFU。

（4）从推荐专用到 LLM 复用。OneTrans 的统一 Transformer 架构可以直接复用 LLM 领域的系统优化——FlashAttention、KV Cache、Tensor Parallelism。这意味着推荐系统可以"站在 LLM 的肩膀上"，复用其成熟的训练和推理基础设施。

（5）Scaling Law 的建立。Wukong 和 Kunlun 首次为推荐系统建立了完整的 Scaling Laws，量化了模型参数、数据量、序列长度的缩放规律。这为工业界选择最优模型规模提供了理论依据——不再是"越大越好"，而是根据 Scaling Law 找到效果-成本的最优平衡点。

（6）MFU 成为核心指标。传统推荐系统以 AUC/CTR 作为核心指标。Scaling Up 时代，MFU 成为与效果同等重要的指标——低 MFU 意味着 GPU 资源浪费，即使效果好的模型也无法大规模部署。RankMixer 将 MFU 从 4.5% 提升到 45%，这比任何算法创新的影响都大。

35.7 工业实践

35.6.1 阿里 LLM 推荐

阿里在 LLM 推荐方面有多项实践：

通义千问推荐增强：使用通义千问大模型为淘宝推荐提供特征增强——生成物品描述、提取用户兴趣画像、推理搭配关系。LLM 特征使推荐 CTR 提升 2-3%。

LLM 推荐理由生成：使用 LLM 为推荐结果生成自然语言解释，提升推荐可解释性和用户信任度。在淘宝"猜你喜欢"场景中，推荐理由展示使 CTR 提升 5-8%。

对话式推荐：淘宝的对话式推荐功能允许用户通过自然语言描述需求，LLM 理解意图后调用推荐模型返回结果。这种交互式推荐在复杂需求场景中效果优异。

35.6.2 百度文心推荐

百度使用文心大模型增强搜索推荐：

语义理解增强：使用文心大模型编码搜索词和物品文本，获取深层语义表示。相比传统 BERT，文心的语义理解能力更强，尤其在长尾查询上提升显著。

知识图谱融合：文心大模型与百度知识图谱结合，为推荐提供知识增强。例如，推理"防晒霜"与"夏季户外"的关联，推荐场景化物品。

35.6.3 Meta 和 Google 的 LLM 推荐

Meta：HSTU 虽然不是传统 LLM，但其大规模 Transformer 架构借鉴了 LLM 的设计理念。Meta 还探索使用 LLaMA 进行推荐理由生成和对话推荐。

Google：Google 使用 PaLM/Gemini 增强搜索推荐。YouTube 推荐系统引入 LLM 理解视频内容和用户评论，提升推荐质量。Google 还探索了生成式召回（Generative Retrieval）在大规模推荐中的应用。

35.6.4 LLM 推荐的工程挑战

推理延迟优化：LLM 推理延迟是工业部署的最大挑战。常用优化手段：

（1）模型蒸馏：将 LLM 蒸馏为小模型用于在线推理，LLM 用于离线特征生成。

（2）量化：INT8/INT4 量化降低推理延迟和显存占用。

（3）异步推理：LLM 推理异步化，不阻塞推荐主链路。LLM 结果缓存后用于后续请求。

（4）分级使用：粗排不用 LLM，精排可选使用 LLM 特征，重排使用 LLM 生成推荐理由。

成本控制：LLM 的推理成本远高于传统模型。需要精细化的成本控制策略——对高价值用户使用 LLM 增强，对普通用户使用传统模型。

效果评估：LLM 推荐的效果评估需要新指标——除了 CTR/CVR，还需评估推荐理由质量、用户满意度、对话轮次等。

35.8 本章小结

大模型正在深刻影响推荐系统的技术路线。本章从 LLM 作为特征增强、LLM 作为推荐引擎、推荐领域基础模型、推荐 Scaling Law 四个维度系统介绍了 LLM 与推荐系统的结合。

当前阶段，LLM 在推荐中的应用以特征增强和推荐理由生成为主，这些应用方式风险低、效果稳定。LLM 作为推荐引擎的探索面临推理延迟和候选集限制等挑战，但在对话推荐和可解释推荐等场景中展现了独特价值。推荐领域基础模型和 Scaling Law 研究处于早期阶段，但代表了推荐系统的重要发展方向。

展望未来，LLM 与推荐系统的融合将更加深入：推荐基础模型可能成为推荐系统的"底座"，各种推荐任务在其上微调实现；LLM Agent 将推荐从被动响应转变为主动交互；多模态大模型将实现真正的多模态推荐。随着大模型技术的快速进步和推理成本的持续下降，LLM 驱动的推荐系统有望成为主流范式。
