在线服务

在线服务是推荐系统面向用户的"门面"——负责接收请求、执行召回、运行模型、返回推荐结果。在线服务的延迟和稳定性直接决定用户体验。在工业实践中，推荐系统的在线服务需要在 50-100ms 内完成全链路推理，同时支撑百万级 QPS。本章将系统介绍推荐系统在线服务的核心组件——服务架构、模型推理、缓存策略和监控告警。

16.1 服务架构

16.1.1 请求路由

推荐系统的在线服务从接收用户请求开始。请求路由负责将请求分发到正确的推荐场景和策略：

场景路由：根据请求来源（首页/搜索/详情页/购物车）路由到不同的推荐策略。不同场景的推荐目标和方法不同——首页推荐重发现，详情页推荐重相似，购物车推荐重搭配。

用户分流：根据用户 ID 哈希将用户分配到不同的实验组。A/B 实验通过用户分流实现，不同实验组使用不同的推荐策略。

流量调度：根据系统负载动态调度流量。高峰期可以关闭部分计算密集型策略（如重排），低谷期全量开启。

16.1.2 微服务化

推荐系统的在线服务通常采用微服务架构，每个环节独立部署：

召回服务：多路召回并行执行。每路召回独立部署，互不影响。召回服务返回候选物品列表。

粗排服务：接收多路召回结果，使用轻量级模型快速过滤。粗排服务要求低延迟（<10ms）。

精排服务：对粗排结果进行精细排序。精排服务使用复杂模型（DIN/MMoE），延迟在 20-50ms。

重排服务：对精排结果进行多样性、公平性调整。重排服务延迟在 5-10ms。

特征服务：提供实时特征查询。特征服务需要支撑高 QPS 和低延迟。

微服务化的优势：独立扩缩容、独立部署、故障隔离。但微服务化也增加了网络开销和调试复杂度。

16.1.3 级联架构

推荐系统的级联架构是在线服务的核心设计：

$$ 召回(万\to千) \to 粗排(千\to百) \to 精排(百\to十) \to 重排(十\to最终) \tag{16.1} $$

每一级的候选集逐级缩小，模型复杂度逐级增加。这种漏斗式架构平衡了效果和效率：

召回层：从全库百万/亿级物品中召回千级候选。使用简单模型（双塔）或规则（热门/类目）快速召回。延迟 <10ms。

粗排层：从千级候选过滤到百级。使用轻量级模型（双塔/DSSM）快速打分。延迟 <10ms。

精排层：对百级候选精细排序。使用复杂模型（DIN/MMoE）和多目标打分。延迟 20-50ms。

重排层：对精排结果进行多样性、公平性调整。使用 MMR/DPP/规则重排。延迟 5-10ms。

总延迟控制：全链路延迟控制在 50-100ms。通过并行化（多路召回并行）、批处理（精排批量推理）和缓存（特征/结果缓存）实现。

16.2 模型推理

16.2.1 推理引擎

模型推理引擎是在线服务的核心，负责加载模型和执行推理：

TensorFlow Serving：Google 开源的模型推理引擎，支持 TF 模型。优点是生态成熟、支持模型版本管理。缺点是对推荐模型的优化不够。

NVIDIA Triton：NVIDIA 的推理引擎，支持多框架（TF/PyTorch/ONNX）。GPU 推理性能优秀，支持动态 batching。

自研推理引擎：大厂通常自研推理引擎。阿里用 xnnpack + 自研推理框架，字节用自研 ByteNN。自研引擎可以针对推荐模型特点（大 Embedding + 小 MLP）做深度优化。

Embedding 查询优化：推荐模型 90%+ 的计算是 Embedding 查询。优化 Embedding 查询是在线推理的关键。使用内存 Embedding 表 + SIMD 查询可以将 Embedding 查询延迟降到毫秒级。

16.2.2 批处理推理

批处理（Batching）是提高推理吞吐量的关键：

请求合并：将多个请求的候选物品合并为一个 batch，一次性推理。GPU 推理尤其受益于 batching。

动态 batching：在请求量波动时动态调整 batch size。高峰期增大 batch 提高吞吐，低谷期减小 batch 降低延迟。

超时控制：等待 batching 的最长时间。超时后即使 batch 不满也立即推理，避免延迟过高。通常设为 5-10ms。

精排 batching：精排通常对 100-200 个候选物品打分。将 100-200 个物品的 embedding 拼接为一个大 batch，一次推理完成所有打分。

16.2.3 模型压缩

模型压缩是在线推理优化的重要手段：

量化（Quantization）：将模型参数从 FP32 量化为 INT8/FP16。INT8 量化可以将推理速度提升 2-4 倍，精度损失通常 <1%。推荐模型对量化友好，因为大部分计算是 Embedding 查询（量化后查询更快）。

剪枝（Pruning）：移除不重要的神经元或权重。推荐模型的 MLP 部分可以剪枝 30-50%，精度损失很小。

蒸馏（Distillation）：用大模型（teacher）蒸馏小模型（student）。精排大模型蒸馏为粗排小模型是常见做法。

算子融合（Operator Fusion）：将多个小算子融合为一个大算子，减少内存访问开销。TensorRT 和 XLA 是常用的算子融合工具。

16.3 缓存策略

16.3.1 多级缓存

推荐系统的在线服务使用多级缓存降低延迟和减轻后端压力：

结果缓存：缓存推荐结果。同一用户短时间内（如 5 分钟）的请求返回相同推荐结果。结果缓存命中率通常 30-50%，大幅降低后端负载。

模型缓存：模型参数缓存在推理引擎内存中，避免每次推理都加载模型。Embedding 表缓存在内存中，支持快速查询。

特征缓存：用户特征和物品特征缓存在 Redis 中。特征缓存命中率通常 80-90%，减少特征服务查询。

Embedding 缓存：高频物品的 Embedding 缓存在推理引擎内存中。避免每次推理都查询 Embedding 表。

16.3.2 缓存更新

定时更新：推荐结果每 N 分钟更新一次。用户短时间内看到相同推荐，但 N 分钟后刷新。

事件触发更新：用户有新行为（点击/购买）时触发推荐结果更新。实时响应用户行为变化。

主动失效：物品下架或价格变化时主动使相关缓存失效。避免推荐已下架物品。

16.3.3 缓存穿透

空值穿透：查询不存在的物品 ID 导致缓存未命中，请求穿透到后端。解决方案：缓存空值或使用布隆过滤器。

热点穿透：热点物品缓存过期时大量请求同时穿透。解决方案：缓存永不过期 + 异步更新，或使用缓存锁。

雪崩：大量缓存同时过期导致后端压力骤增。解决方案：缓存过期时间加随机抖动，或分级过期。

16.4 降级与容错

16.4.1 降级策略

当系统压力过大或部分服务故障时，降级策略保证基本可用：

模型降级：精排模型故障时降级为粗排结果或热门推荐。保证推荐不中断，虽然效果下降。

召回降级：多路召回部分故障时，使用剩余召回路的结果。如向量召回故障，使用热门和类目召回。

特征降级：实时特征服务故障时，使用离线特征或默认值。保证推理不中断。

重排降级：重排服务故障时直接返回精排结果。重排是"锦上添花"，可以跳过。

16.4.2 熔断与限流

熔断（Circuit Breaker）：下游服务错误率过高时自动熔断，直接返回降级结果。防止故障传播。Hystrix 和 Resilience4j 是常用熔断框架。

限流（Rate Limiting）：限制请求速率，防止过载。推荐系统通常使用令牌桶或漏桶算法限流。高峰期限流保护系统，低谷期放开限制。

队列控制：请求队列长度限制。队列过长时拒绝新请求，防止延迟雪崩。

16.5 监控与告警

16.5.1 延迟监控

全链路延迟：从请求到响应的端到端延迟。通常要求 P99 < 100ms。使用直方图或分位数监控。

各环节延迟：召回/粗排/精排/重排各环节的延迟分布。定位瓶颈环节。

延迟异常告警：延迟突增时告警。可能原因：流量激增、模型变更、缓存失效。

16.5.2 效果监控

实时 CTR/CVR：实时监控推荐效果。CTR 突降可能表示模型故障或数据异常。

多样性监控：推荐列表的类目分布和覆盖率。多样性下降可能导致用户体验下降。

冷启动监控：新物品的曝光比例和点击率。过低的新物品曝光比例表示推荐系统缺乏发现能力。

16.5.3 异常检测

数据异常：特征缺失率突增、行为日志量异常。可能表示数据管道故障。

模型异常：预测分数分布异常、输出方差过大。可能表示模型 bug 或特征穿越。

系统异常：CPU/内存/网络异常。通过基础设施监控发现。

16.6 工业实践

16.6.1 淘宝在线架构

淘宝推荐系统的在线架构是工业级标杆：

接入层：API Gateway 负责请求路由和用户分流。支持 A/B 实验和灰度发布。

召回层：多路召回并行执行，包括向量召回（FAISS）、图召回、热门召回、类目召回。总延迟 <10ms。

排序层：粗排（双塔）+ 精排（DIN/MMoE）+ 重排（DPP）。精排使用 GPU 推理，延迟 30-50ms。

特征层：实时特征服务（基于 Redis + 自研特征服务），延迟 <5ms。

总延迟：P99 < 80ms，支撑千万级 DAU。

16.6.2 抖音在线架构

抖音推荐系统的在线架构以实时性和高 QPS 为特色：

实时特征：用户最近 5 分钟的行为序列实时更新。实时特征延迟 <1s。

在线学习：精排模型每 5 分钟在线更新。快速适应新趋势。

GPU 推理：精排使用 GPU 推理，支撑百万级 QPS。动态 batching 优化吞吐量。

总延迟：P99 < 50ms，支撑亿级 DAU。

16.7 本章小结

在线服务是推荐系统面向用户的"门面"，需要在 50-100ms 内完成全链路推理。本章介绍了在线服务的核心组件——服务架构（微服务化/级联架构）、模型推理（推理引擎/批处理/模型压缩）、缓存策略（多级缓存/缓存穿透防范）、降级容错（降级/熔断/限流）和监控告警（延迟/效果/异常）。

在线服务的核心设计原则是：低延迟、高可用、可降级。低延迟保证用户体验；高可用保证服务不中断；可降级保证故障时基本可用。这三者构成了推荐系统在线服务的"铁三角"。

随着模型规模的增长（如 HSTU 百亿参数），在线推理面临越来越大的延迟压力。模型压缩、推理优化和专用硬件（如推荐 ASIC）是在线服务的发展方向。同时，生成式推荐的端到端架构有望简化在线服务——从多级级联变为单次推理，可能降低架构复杂度但提高单次推理要求。
