在线服务

推荐系统的在线服务直接面向用户请求，需要在数十毫秒内完成从召回、排序到结果返回的全流程。在线服务的性能和稳定性直接决定了用户体验。本章将介绍推荐系统在线架构中的核心组件与关键技术。

16.1 推荐请求链路

一次完整的推荐请求链路通常包括：客户端发起请求→服务端转发→召回（多路并行）→粗排→精排→重排→混排→结果返回。整个链路的端到端延迟通常控制在 200-500ms 以内，其中推荐系统内部耗时通常在 50-100ms。

16.2 模型推理服务

16.2.1 推理引擎

推荐模型的在线推理通常使用 TensorFlow Serving、TensorRT 或 ONNX Runtime。TensorRT 通过算子融合、精度量化（FP16/INT8）、内核自动调优等优化大幅降低推理延迟，是工业界高性能推理的首选引擎。

16.2.2 推理加速技术

  • 算子融合：将多个小算子合并为大算子，减少 GPU 内核启动开销
  • 精度量化：将 FP32 量化为 FP16 或 INT8，减少显存占用和计算量
  • 知识蒸馏：用大模型训练小模型，在保持效果的同时降低推理成本
  • 模型并行：将大模型拆分到多个 GPU 上并行推理
  • 请求批处理：将多个请求合并为一个 batch，提高 GPU 利用率

16.3 特征服务

在线推荐需要实时获取用户特征和物品特征。工业界通常采用多级缓存策略：

  • L1 本地缓存：使用 LRU 缓存热点用户/物品特征，延迟 < 1ms
  • L2 Redis 集群：存储全量特征，延迟 2-5ms
  • L3 HBase/Hive：存储历史特征，延迟 10-50ms

16.4 降级与容灾

16.4.1 降级层次

  • 特征降级：当特征服务异常时，使用默认特征或缓存特征替代
  • 模型降级：当精排模型超时或异常时，回退到粗排结果或更简单的模型
  • 召回降级：当部分召回源异常时，使用其他召回源或缓存结果补充
  • 热榜兜底：当推荐系统完全不可用时，返回全站热门内容作为兜底

16.4.2 DCAF 动态算力分配

DCAF [1] 是阿里巴巴提出的动态算力分配框架。它将资源分配建模为带约束的背包问题，根据请求价值和算力预算动态选择最优推理策略。通过拉格朗日对偶分析，最优策略简化为选择使 Qᵢⱼ - λqⱼ 最大的动作，其中 λ 通过二分搜索求解。DCAF 实现了"按请求价值进行差异化降级"，在业务收益与系统成本之间取得更优平衡。

16.5 监控与告警

推荐系统在线服务需要完善的监控体系：服务层监控（QPS、P50/P99 延迟、错误率、GPU 利用率）、数据层监控（特征缺失率、特征分布漂移、索引更新延迟）、模型层监控（pxtr 均值与分布、PCOC 校准指标、AUC 异常）、业务层监控（各业务流量占比、多样性指标、冷启动曝光率）、降级监控（降级触发次数、降级流量占比、兜底内容占比）。

16.6 本章小结

本章系统介绍了推荐系统的在线服务架构。推荐请求链路从客户端到结果返回需要在数百毫秒内完成全流程。模型推理服务通过算子融合、量化、蒸馏等加速技术降低延迟。特征服务采用多级缓存策略。降级与容灾机制通过多层降级保障服务连续性。监控体系覆盖服务、数据、模型、业务和降级五个维度。
